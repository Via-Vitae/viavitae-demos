# Content Policy — viavitae-demos

This document governs all content in every demo template. It is binding on every
contributor and every pull request.

---

## 1. Fictional entities

Every organisation, person, address, phone number, email, and registration number
shown in a demo is **fictional**. Names are generated by `shared/lib/fictional.ts`
using a deterministic seed (fixed Faker seed per template).

- No real parish, diocese, funeral home, or business name may appear in a demo.
- No real person's name may be used for clergy, staff, vendors, or customers.
- Fictional names must be plausible for the Lithuanian context but must not
  correspond to a real entity. Verify with a web search before committing.

## 2. Disclaimer banner

Every demo page displays a visible disclaimer banner (`DemoBanner` component) in
the visitor's locale (LT/EN/RU). The banner states:

> This is a demonstration website. All entities, persons, and data shown are
> fictional. This is not a real organisation.

The banner must:

- Be visible on every page without scrolling.
- Not be dismissible (it is not a cookie banner).
- Include a "Make it mine" call-to-action linking to the assessment funnel.

## 3. Liturgical imagery

Real liturgical imagery (photographs of churches, liturgy, sacred art) may be used
in demos under the following conditions:

- Every image must be either CC0 (public domain) or the photographer's own work.
- Every image must be registered in `shared/seed/media-manifest.json` with:
  - `path`: relative path from the template's `seed/media/` directory.
  - `licence`: SPDX identifier (`CC0-1.0` or `Proprietary` for own work).
  - `source`: photographer name or "own photography".
  - `alt_lt`, `alt_en`, `alt_ru`: trilingual alt-text (all three required).
- CI enforces: every file in `seed/media/` must have a matching manifest entry.
  Unlicensed images fail the build.
- No imagery depicting real identifiable persons may be used without a model release.

## 4. Stripe and payment demos

- All payment flows use Stripe **TEST mode** exclusively.
- Test-mode API keys (`sk_test_*`, `pk_test_*`) may appear in `.env.example` with
  placeholder values. Live keys (`sk_live_*`, `pk_live_*`) are **never** committed.
- The reset mechanism asserts that no live Stripe keys exist in any `seed/` directory.
- A visible "TEST MODE" banner appears on all checkout and donation pages.

## 5. CRM and third-party data

- The CRM dashboard demo (`basilica/crm-dashboard/`) uses **hardcoded fictional data**
  only. It must never connect to a real Bitrix24 instance.
- Any third-party service integration (Cal.com, MapLibre, analytics) must:
  - Use only fictional or mock data in demos.
  - Be checked for EEA data residency compliance.
  - Have a DPA in place before connecting to any real service.

## 6. AI-generated content

- The AI Pastoral Assistant demo (`basilica/ai-pastoral/`) must:
  - Show citations for every claim.
  - Never generate content that claims to be official church teaching.
  - Display a clear notice that responses are AI-generated and not pastoral advice.
  - A DPIA is required before this demo goes live (processes user queries).

## 7. Internationalisation

- All user-facing strings must be provided in LT, EN, and RU.
- PL and DE are stub locales (English fallback) until content is translated.
- String keys are shared via `shared/lib/i18n-messages.ts`.
- Parity is enforced in CI: missing keys in LT/EN/RU fail the build.

## 8. Accessibility

- All demos must meet WCAG 2.2 AA.
- axe-core runs in CI and in the nightly Playwright smoke test.
- Every image has alt-text (trilingual for liturgical imagery).
- Every form control has a programmatic label.
- Every interactive element has a keyboard-accessible path and visible focus state.

---

This policy is reviewed when a new template is added or when a content concern is
raised. Changes are recorded in `CHANGELOG.md`.
